## Why Railway, not Supabase + cron

This is Charles's reasoning, carried forward close to verbatim because it's
the actual rationale and shouldn't get flattened into "Railway vs Supabase"
in future summaries — **it was never really a database choice.**

The driver is the scan job model. A pool run hits three AI channels
(ChatGPT, Google AI Mode, Perplexity) per query, then runs an LLM
classification pass over each transcript. That's long-running background
work with real failure modes — a queue-and-worker problem (retries on failed
channel calls, backpressure as query/merchant volume grows, visibility into
what's mid-flight), not a fixed-schedule fire-and-forget job. Cron
(GitHub Actions included) has practical ceilings that bite here: 5-minute
minimum granularity, metered minutes past the free allowance, and no
persistent process — every run starts cold, rebuilding state rather than
having a worker sit and drain a queue. Redis is in this stack specifically to
back that job queue, not as a cache — that's the piece a pure cron model has
no natural home for.

Railway won out over the other options actually compared: Vercel's function
timeouts rule it out for long-running work; Fly.io does the same
worker/queue/Postgres/Redis model fine but is usage-billed with no hard
ceiling, which matters at bootstrapped-budget scale; Railway gives the same
model with hard spend caps.

Supabase itself was never ruled out on Postgres merits — "Railway Postgres vs
Supabase Postgres" was never really the question. Supabase's edge is bundled
auth/storage tooling this project doesn't need yet.

**Status: confirmed.** The Railway call was originally made without Steve's
input on the ops side, but has since been discussed and agreed — Railway is
the settled architecture for the scan pipeline, not a provisional choice.
The reasoning above is kept in full because it's the actual rationale and
worth having on hand, not because the decision is still open.

## Changelog note — brand-list redesign (v2)

Early real-world testing surfaced a genuine design bug: `query_results`
originally stored a single `state` + `competitor_brand` pair, which only
makes sense relative to one specific brand. Phase 1 has no merchant yet to
be that brand, so the code silently defaulted to whichever brand happened to
be listed first in `brands.json` — which produced a confusing, sometimes
self-contradictory result (a brand being both the implied "target" and its
own "competitor" in the same row).

Fixed by replacing those two columns with `recommended_brands` and
`cited_brands` — the raw fact of which brands an answer recommended vs.
merely mentioned, with no target brand baked in at collection time. "Was
brand X recommended" becomes a free lookup against already-stored data for
any brand, computed whenever it's actually needed (e.g. per-merchant in
Phase 2), via the `brand_mentions` view in `db/schema.sql`. If you're
picking up a database that already ran the old schema, apply
`npm run migrate:v2` once (see Setup) before the new code will work against
it.

## Changelog note — mentions restructure (v3)

Charles's "Data Dependencies for Steve" doc asked for two things that turned
out to be the same underlying change: per-mention product name + exact
quote (`products[]`), and an explicit `mention_type` on competitor mentions.
Both come from the same classification pass over the same transcript, so
`query_results.recommended_brands`/`cited_brands` (two flat text arrays)
were replaced with a single `mentions` jsonb array — one object per brand
mention, carrying `brand`, `mention_type`, `product_name` (nullable), and
`quote` (nullable). Captured for every brand mentioned, not just the
merchant's own — there's no extra collection cost to this, and it resolves
the doc's open "hard boundary or not" question: whether a future API
exposes competitor product-level detail becomes a pure serving-layer
decision, same principle as existing tier gating, not something the
collection layer needs to pre-decide. See `db/schema.sql`'s comment on
`query_results` and the `brand_mentions` view for the query patterns this
enables. If you're picking up a database that already ran the v2 schema,
apply `npm run migrate:v3` once (see Setup) — this one preserves existing
data (backfills old rows with `product_name`/`quote` = null) rather than
dropping it, since real paid-for pool data exists by this point.

## What this is

- Postgres schema matching the Summary doc's data model: `categories` →
  `subcategories` → `queries`, plus `shops`, `scans`, `query_results`
  (3-state), `subscriptions` (`db/schema.sql`)
- Starter seed: the same 60 queries from the original build, restructured
  under 2 subcategories per flagship category — chosen to match the league
  table starting depth so the same subcategories serve both (`db/seed.sql`)
- Three channel modules — Google AI Mode (DataForSEO), ChatGPT (OpenAI API
  proxy), Perplexity (Perplexity API) — each returning a common
  `{ transcript, references, raw_response }` shape (`src/lib/channels/`)
- A classification pass using Claude to turn a transcript into
  `{ state, competitor_brand }` (`src/lib/classify.js`)
- A BullMQ queue + persistent worker that processes one job per
  (query × channel) pair, with retries and backpressure (`src/worker.js`)
- A thin scheduler process that only enqueues jobs on a cron tick — it does
  no channel calls or classification itself (`src/scheduler.js`)
- A manual trigger script with the same `DRY_RUN` / `MAX_QUERIES_PER_RUN`
  workflow as the original build, for smoke-testing without waiting on the
  schedule (`src/scripts/enqueuePoolRun.js`)

## Channel caveats — read before trusting any single channel's numbers

- **Google AI Mode**: same deviation as the earlier build — uses DataForSEO's
  `ai_mode/live/advanced` endpoint rather than Google Shopping API, because
  it returns endorsement/citation language and Shopping doesn't. The `type`
  field match in `googleAiMode.js` is still inferred from docs, not confirmed
  against a live response.
- **ChatGPT**: there is no public API for the ChatGPT consumer product
  itself. This channel calls the OpenAI Chat Completions API as a proxy —
  same model family, different retrieval/browsing behaviour from what a
  person actually sees in the app. Prior project research also flagged that
  ChatGPT's shopping results lean heavily on Google Shopping data, which this
  channel can't observe at all. Treat its output as directional, not a
  confirmed measure of ChatGPT-the-product.
- **Perplexity**: the closest of the three to a real analog — the API models
  genuinely browse and return citations, the same mechanism the consumer
  product uses.

## Classification caveat

`classify.js` is an LLM classification pass over free text (Claude), not the
NLP claim-extraction pipeline described in the SDX:VibeEvidence work. It's a
real improvement on the old regex + `brands.json` approach — it handles
paraphrase and negation a regex can't — but it should still be spot-checked
against `query_results.raw_response` before trusting frequency numbers.

## Phase 1 vs Phase 2 — what `scans` means right now

There are no merchants yet. The scheduler creates one "pool scan" per
category per cadence tick with `shop_id = null`; its `query_results` are the
shared pool data every future merchant will read from. From Phase 2 onward, a
real merchant-triggered scan gets its own row with `shop_id` set — whether
that snapshots existing pool results or triggers fresh channel calls for that
merchant's category is a Phase 2 product decision, not resolved here. See the
`scans` table comment in `db/schema.sql`.

Relatedly: the shared-pool cadence in this build is one weekly cron
(`POOL_CRON`) for everything. Free (weekly) vs Essential (daily) per-plan
cadence from the Summary doc, Section 3, needs per-shop scheduling once real
subscriptions exist — expect `scheduler.js` to grow a per-plan schedule (or a
DB-driven schedule table) at that point, not stay a single cron expression.

## Search volume

`queries.search_volume` is populated by a separate, periodic script — not
part of the worker's continuous scan loop, since real search volume doesn't
meaningfully change scan-to-scan the way AI answers do. Running it
unnecessarily just spends money for no new information.

```
railway ssh -s citational-pool -- npm run search-volume
```

This calls DataForSEO's Keyword Data API (`keywords_data/google_ads/search_volume/live`)
— a different DataForSEO product from the AI Mode endpoint used for the
actual channel calls, but billed to the same account/credentials already
set up. UNVERIFIED — not run against a live account in this build session;
check the console output against what's actually in the `queries` table
after the first run, same as any other unverified endpoint in this project.

A `NULL` search_volume after running this means DataForSEO measured no
meaningful volume for that exact phrase — a real answer, not a failure.
Re-run this occasionally (e.g. monthly) rather than on every deploy.

## Setup

1. **Railway**: create a project, add a **Postgres** service and a **Redis**
   service. Then, in each other service that needs them (worker, scheduler),
   go to that service's **Variables** tab and add a *reference variable* —
   type `DATABASE_URL` as the name, and for the value use Railway's
   autocomplete (type `$`) to select `${{Postgres.DATABASE_URL}}`. Do the
   same for `REDIS_URL` → `${{Redis.REDIS_URL}}`. This isn't fully automatic
   — it's one dropdown pick per variable per service, not a raw copy-paste.
2. Add **two more Railway services** from this repo, each with its own start
   command:
   - `npm run worker` — the persistent worker
   - `npm run scheduler` — the cron-tick scheduler
   Both need the env vars below; Railway shares `DATABASE_URL`/`REDIS_URL`
   across services in the same project automatically.
3. Copy `.env.example` to `.env` for local dev (or set the equivalents as
   Railway service variables): DataForSEO login/password, `OPENAI_API_KEY`,
   `PERPLEXITY_API_KEY`, `ANTHROPIC_API_KEY`.
4. `npm install`
5. Apply the schema (Railway's Postgres has no built-in SQL editor the way
   Supabase's dashboard did):
   ```
   npm run migrate
   ```
6. Smoke test without spending anything or touching the DB:
   ```
   npm run enqueue:dry
   ```
7. Small capped real run — start the worker in one terminal, enqueue a
   handful of jobs in another:
   ```
   npm run worker
   MAX_QUERIES_PER_RUN=5 npm run enqueue
   ```
   Then check `query_results.raw_response` in Postgres to confirm the real
   shape from each channel, and check `state`/`competitor_brand` against the
   transcript to sanity-check the classification pass.
8. Once that looks right, run the full pool (`npm run enqueue`), let the
   scheduler take over on its cron tick from there.

## What's deliberately NOT built yet

- **No merchant-facing anything.** No Shopify app, no dashboard, no billing.
  `shops` and `subscriptions` tables exist in the schema (per the Summary
  doc's data model) but are empty — that's Phase 2.
- **No competitor auto-discovery.** `target_brands` and `brands.json` are
  manually maintained. Fine at pool-validation scale, won't scale past a few
  hundred brands.
- **`competitor_brand` extraction is untested against real data.** The
  classification prompt enforces brand-level-only, never product-level, but
  that's only been checked by reading the prompt, not by running it.
- **No historical/time-series schema for the league tables** (Summary doc
  Section 6) — that's a separate open item, not attempted here.
- **Custom/merchant-submitted queries** are anticipated in the schema
  (`queries.source` includes `merchant_custom`) but not implemented anywhere
  — deliberately left as a future Pro-tier gate per Summary doc Section 3.
